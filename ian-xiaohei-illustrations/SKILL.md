# Ian 小黑怪诞正文配图

## 核心定位

为中文文章设计和生成正文配图（默认 16:9 横版，可参数化为其他比例）。目标不是做商业插画、PPT 信息图或可爱卡通，而是把文章里的关键判断、流程、结构、状态或隐喻，变成一张清爽、怪诞、有创意、可读但不说明书的手绘解释图。

默认视觉 IP 是“小黑”：黑色实心、白点眼、细腿、空表情，认真做一件荒诞但成立的事。小黑必须参与画面的核心动作，不能只是站在旁边当装饰。

## 先读这些参考

按任务需要读取，不要一次塞满上下文：

- `references/style-dna.md`：风格 DNA、颜色、文字、禁忌。
- `references/xiaohei-ip.md`：小黑 IP 的形象、性格、动作库和禁忌。
- `references/composition-patterns.md`：结构类型、原创隐喻方法和反复刻规则。
- `references/prompt-template.md`：单张生图提示词模板。
- `references/qa-checklist.md`：生成后检查和迭代规则。
- `references/custom-ip-template.md`：自定义 IP 角色的模板文件（复制到 `references/custom-ip.md` 后填写）。
- `references/custom-style-template.md`：自定义风格的模板文件（复制到 `references/custom-style.md` 后填写）。
- `references/manifest-template.md`：每篇文章的产出清单模板（复制到 `manifest.md` 后填写）。
- `assets/examples/`：只作低频视觉校准，不进入默认生成路径。不要照抄这些案例的构图、物件或标注。

## 可调整的轴（比例 / 风格 / 语言）

这三项是可调参数，都有**向后兼容的默认值**——不碰它们，行为就和现在一样；需要时再设置。

- **画面比例** (`aspect_ratio`) — 默认**16:9**（正文配图）。社交媒体可用 **1:1**，移动端或 Notion 可用 **9:16 / 3:4**。将此参数传递给图像工具，并记录在清单中。构图规则不变，只是画框变了。
- **风格配置文件** — 默认是 `references/style-dna.md`（白底、黑线、少量红橙蓝）。要更改调色板、线条或背景，可将 `references/custom-style-template.md` 复制为 `references/custom-style.md` 并使用它。结构类型、一图一意、角色承担核心动作等规则在任何风格下都保持不变。
- **标注语言** (`annotation_lang`) — 默认**中文**。可选：`en` (英文)；或 `bilingual` (主要标注+小字号的第二语言注释)。这只改变标注的语言，不改变视觉风格。在文字渲染较弱的工具上（如 Flux 系列），拉丁字母渲染最可靠，可优先用英文或双语。

当自定义风格、非默认语言或非 16:9 比例生效时，在提示词模板和 QA 环节所有引用默认值的地方都应用它。

## 自定义 IP 角色（替换小黑）

小黑是**默认**角色，不是强制要求。用户可以用自己的吉祥物或图标替换它；其他一切（当前生效的风格、颜色、构图规则）都保持不变。

有两种方式设定自定义 IP：

- **通过描述** — 用户描述角色的（形状、眼睛、四肢、气质）。使用 `references/custom-ip-template.md` 作为模板，将内容记录在 `references/custom-ip.md` 中。
- **通过样本图片** — 用户给一张参考图（他们的 logo、吉祥物或图标）。读取图片，用**文字**描述其轮廓、眼睛、四肢和感觉，起草 `references/custom-ip.md`，并在生成前与用户确认。这里的文生图工具是从这份文字描述中渲染，而不是从图片本身；同时锁定一个固定的 `seed`，以保持角色在多张图片中的一致性。

**所有自定义 IP 都必须继承一条规则：** 角色必须**承担核心动作**，不能只是装饰。如果去掉它之后，图片的核心隐喻仍然完全成立，那么它就只是个摆设——这条规则对任何角色都不可协商。

当自定义 IP 生效时，在提示词模板中所有提到“IP 角色”的地方都使用它；否则默认使用小黑（`references/xiaohei-ip.md`）。

## 工作流

### 1. 消化正文

先读用户给的正文、链接、Notion 页面、Markdown 文件或截图内容。提炼：

- 核心观点是什么
- 哪些段落承担认知转折
- 哪些内容适合用图解释
- 哪些地方只适合文字，不需要图

不要平均配图。优先选择“认知锚点”，例如：核心判断、两个断点、输入输出闭环、分流、前后对比、一鱼多吃、承接路径、常见坑、角色状态变化。

### 2. 先出配图策略

首先为整篇文章选定一个**视觉母题**——一个共用的世界 / 物件家族 / 场景 / 道具，让所有图片像一本速写本，而不是 N 张无关插图。把母题记录在清单（第 5 步）并在整篇文章中复用；每张图仍然只表达一个核心意思——母题是共用的「皮肤」，不是重复的构图。

如果用户只是说“分析怎么配图 / 思考哪些地方需要配图”，先给 shot list。每张图写清楚：

- 放在哪个段落后
- 图的主题
- 核心意思
- 结构类型
- 当前 IP 角色在图里做什么
- 建议元素
- 建议标注词（默认中文）

默认 4-8 张。文章很短时 1-3 张；长文也不要轻易超过 9 张。够用就好，避免把正文做成画册。

### 3. 单张生成（工具无关）

**成本软确认：** 如果用户明确要求“生成 / 输出 / 做图”，对于 1-3 张图，直接生成；若**超过 3 张**，则先展示配图策略，并附上一句提示（“共 N 张图，使用`<工具名>`生成；图像生成通常按张数计费”），获得简单同意后再批量生成。不要一声不响地铺开十几张图的渲染。

首先解析**当前 IP 角色**：如果用户提供了自定义 IP（通过描述或样本图片），则使用 `references/custom-ip.md`；否则默认使用小黑。

按以下优先级选择图像生成工具（不要写死某一家）：

1.  有内置 `image_gen`（Codex）→ 直接用。它对图内文字支持最好，且支持编辑/修复。
2.  有图像生成 MCP（如 `mcp__image-gen__generate_image`，设 `aspect_ratio`（默认 "16:9"）、`output_format="png"`、`num_outputs=1`）→ 用它。文生图模型（Flux 系）渲染英文尚可，中文则较弱：优先用英文或双语标注，并把标注压到 2-4 个、每个尽量 ≤4 字，降低错字风险。
3.  没有任何图像工具 → 不要假装生成；按 `references/prompt-template.md` 为每张图输出「可直接粘贴到外部生图工具」的英文提示词，这也是合格交付，不是失败。

**Seed 纪律（角色一致性 + 可复现性）：** 为整篇文章选择一个整数种子（seed），并将其传递给每个图像的生成工具（在支持 seed 的后端上，如 Flux；不支持的后端如 GPT-image / Codex `image_gen` 则通过稳定的文本描述来保持角色一致），这样反复出现的角色在所有图像中都能保持视觉上的一致。在清单（步骤5）中记录每张图的 seed。要重新生成单张图而不影响其他图，只需更改该图的 seed。如果当前 IP 配置文件定义了 `seed`，则以它为基础。

每张图只讲一个核心结构。提示词必须包含：选定的画面比例（默认 16:9）；纯白背景（或当前风格配置）；黑色手绘线稿；少量红/橙/蓝手写标注（默认为中文）；大量留白；当前 IP 角色作为核心动作的主体；并禁止 PPT/商业/可爱/复杂架构/左上角标题。

**无字模式（可选，稳健）：** 生成不带任何图内标注的图片，并将本应有的标注作为普通文字写在图片下方。当图内文字很重要但渲染器较弱时（例如 Flux 处理中文），或者当用户想要干净的无标注图片时，使用此模式。图片承载隐喻，文字说明承载语言。这完全绕开了最常见的失败模式（文字乱码）。它既是一个预先的刻意选择，也是第4步回退的目标——应用于整篇文章，而不是逐张图片应用；如果预先选择此模式，则该篇文章跳过第4步的文字验证重试循环。

不要复刻过往案例。案例只提供风格密度和小黑参与方式，不能直接复用“传送带断点 / 小黑拉线 / 素材鱼 / 盖章工具箱 / 常见坑路径”等已有构图，除非用户明确要求复刻某张图。每次都要从当前文章重新发明一个奇怪但成立的隐喻。

### 4. 检查与迭代

生成后检查 `references/qa-checklist.md`。如果出现以下问题，优先重生成或局部编辑：

- 当前 IP 角色只是装饰
- 画面太满
- 太像流程图/PPT
- 中文太多或错字严重
- 左上角出现“常见坑/流程图/系统架构图”等标题
- 画风太可爱、幼稚、死板
- 背景不是干净白底

**验证渲染文字（最常见的失败点）：** 生成后，回头看你刚产出的图片，把上面的手写字读一遍。如果任何标注出现乱码、错字或词不达意，用更少/更短的标注词重新生成，或者（在文字渲染弱的工具上）换成英文/双语，或者退回到**无文字的图片+图下文字说明**的模式。每个图最多重试约2次；如果文字仍然失败，交付无文字的图片+说明，而不是交付乱码。

### 5. 保存交付

如果用户在 workspace 内工作，把最终图复制到 `assets/<article-slug>-illustrations/` 目录下，并按 `01-topic.png`, `02-topic.png` ... 的顺序命名。保留原始生成文件，不要覆盖已有资产，除非用户明确要求替换。

在图片旁边，使用 `references/manifest-template.md` 模板写入 `manifest.md` 文件，记录每张图的文件名、在文章中的位置、主题、结构类型、seed、使用的工具、单行 alt-text，以及（在模板的 Prompts 部分）所用的确切提示词。这使得每张图片都可复现和独立重生成，并且 alt-text 解决了无障碍性问题（用于博客、Notion、屏幕阅读器）。

## 输出口径

生成前的策略输出要短而准。生成后的交付要包含：

- 生成了几张
- 每张图的用途
- 保存路径
- 哪些图最稳，哪些图是可选

不要长篇解释风格理论；让图自己说话。
